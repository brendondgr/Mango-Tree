# UI audit — Mango Tree web workspace

**Date** 2026-08-31 · **Scope** [`docs/audit-profile.yaml`](audit-profile.yaml) ·
**Remediation plan** [`docs/overhaul-plan.md`](overhaul-plan.md)

---

## 1. Summary

**185 findings: 38 blocker, 95 major, 52 minor.**

Three things matter more than the rest:

1. **The app does not work on a phone.** Not "is cramped on a phone" — is inert.
   Below 820px a transparent `position: fixed` wrapper covers the whole viewport
   and swallows every tap in the main body, and the chat drawer's own backdrop
   paints *above* the drawer at `z-90` versus `z-20`. Verified with real taps:
   the launcher cards cannot be tapped, the composer cannot be typed into, and
   the send control sits 23px below the bottom edge. Mobile friendliness is the
   owner's stated first priority, so this is the whole report in one finding.

2. **The initial download is 7,855 kB of JavaScript in a single chunk**
   (3,251 kB gzipped) — roughly 13× the budget for an app-like SPA. 70% of it is
   `js-tiktoken`'s six BPE rank tables, pulled in by a barrel import for a
   fallback code path, and paid for by anyone who only ever sees the login page.
   Nothing is code-split: all eight app UIs load before the first paint.

3. **The eight app modules are eight different products.** They were ported in
   from standalone apps and never converged: four incompatible strategies for
   categorical colour, four competing tab languages, 1,649 lines of bespoke CSS
   in two modules alone, and 38 hardcoded hex literals that ignore the theme
   system entirely. `media_viewer` is the counter-example and the model —
   zero bespoke CSS, explicit loading/error/empty states.

Underneath those: every text input renders at 14px, so iOS Safari auto-zooms on
the first tap of the login form; the focus ring is below 3:1 contrast on two of
the eight themes, which defeats the keyboard-operability goal exactly where it
was asked for; and all shadcn overlay animations are dead classes because no
animate plugin is installed, so every dialog, popover and lightbox is a hard cut.

**What is already good,** and worth saying because it shaped the plan: all eight
themes define the same 57 tokens with zero drift and a test that enforces it;
`tsc --noEmit` and 75/75 vitest cases are green; `!important` appears three
times and all three are legitimate; there are no `as any` casts and no
`@ts-ignore` anywhere; and the shell is built on real `<button>` elements and
Radix primitives rather than the usual `div onclick` epidemic. The foundations
are sound. The problem is that the structure did not keep up with the growth to
eight app modules.

## 2. Scope and method

Twelve parallel review passes over the full frontend (`web/src` plus the eight
`utils/apps/*/frontend` modules, ~30,000 lines), each reading the slice of the
audit ruleset matching its dimension. Findings were then merged and de-duplicated
by `file:line`; a `×N` marker in the tables below means N independent passes
reported the same defect, which is corroboration rather than duplication.

Measured against the **rendered, authenticated** site, not the source:

| Instrument | What it produced |
| --- | --- |
| `utils/scripts/audit_ui.py` | axe-core, overflow, touch targets, input font sizes, tab-order shape across 9 surfaces × 3 viewports |
| `utils/scripts/verify_mobile.py` | Real taps at 390×844 — hit-testing what a finger actually lands on |
| `npm run build` | Chunk inventory and byte counts |

Both scripts are committed and re-runnable, which is what makes every finding
below falsifiable and every fix verifiable.

### What was NOT checked

Stated as deliberately as what was, because a tool's silence is not a pass.

- **Real devices.** Everything is Chromium at emulated viewports. iOS Safari's
  auto-zoom and dynamic-toolbar behaviour are inferred from the measured
  font-sizes and `100vh` usage, not observed on hardware.
- **Field performance.** The bundle numbers are lab measurements from a local
  build. There is no CrUX or RUM data for this deployment, so no claim is made
  about real-world LCP or INP.
- **Screen readers.** No NVDA/JAWS/VoiceOver pass was run. Automated testing
  reaches roughly 30–40% of WCAG issues; the accessibility findings here are the
  floor, not the ceiling.
- **The long tail.** The blockers and the headline findings were reproduced on
  the rendered page. Many minor findings come from the code-reading pass and are
  triaged but not individually re-measured in a browser.
- **Backend behaviour** beyond what the UI exercises.

### A note on severity

`compliance.regime` is `none` — this is a personal single-owner tool with no
statutory obligation — so WCAG failures are **not** auto-escalated to blocker as
they would be for a covered site. They are graded by user impact. Where a WCAG
failure is marked blocker below, it is because the feature is genuinely
unreachable, not because a standard was cited. That classification would change
if the site's legal status ever changed.

## 3. The four verified mobile failures

These were reproduced with real taps at 390×844, and they are why Phase 3 of the
plan comes before any cosmetic work.

| Check | Result |
| --- | --- |
| Tap the first Apps launcher card | Lands on `div.flex.h-full.shrink-0` — a `fixed`, 844px-tall, transparent wrapper. `.tap()` times out. |
| Open the chat drawer, tap the composer | Lands on `button.fixed.inset-0.z-[90]` — the backdrop, painting above the drawer it reveals. |
| Type a message | Fails. The chat is unusable below 820px. |
| Send control position | `bottom: 867px` in an 844px viewport. |

Reproduce with:

```bash
MANGO_AUDIT_USER=you MANGO_AUDIT_PASSWORD=yourpassword uv run utils/scripts/verify_mobile.py
```

## 5. Remediation sequence

Findings ordered by severity is a report; findings ordered for work is a plan,
and they are different orders. The sequence lives in
[`docs/overhaul-plan.md`](overhaul-plan.md) and is grouped so that systemic
fixes land before individual instances — one design-token change closes more
findings per hour than any number of one-off edits.

| Order | Phase | Rationale |
| --- | --- | --- |
| 1 | Design foundations (tokens, z-scale, motion, contrast) | One change resolves findings across every surface |
| 2 | Shared primitives (skeleton, field, master-detail, sheet, dialog) | Removes the reason each app hand-rolls its own |
| 3 | Shell rebuild, mobile-first | Stops the bleeding — the app is unusable on a phone today |
| 4–5 | Chat, landing, auth, onboarding, settings | Highest-reach surfaces |
| 6 | App modules | The long tail, batched by module rather than by defect type |
| 7 | Performance | Independent of the above; verified per step against `dist/assets` |
| 8 | Multi-provider LLM | Feature work, gated on its own denial tests |
| 9 | Re-audit as a diff | Without this, the fixes are assumptions again |

## 6. Re-auditing

This report is a baseline. Re-run both instruments and compare — a fix nobody
re-tested is an assumption.

```bash
MANGO_AUDIT_USER=you MANGO_AUDIT_PASSWORD=yourpassword uv run utils/scripts/audit_ui.py --out .audit/after
```

`audit_ui.py` exits non-zero on page-level horizontal scroll or any critical axe
violation; `verify_mobile.py` exits non-zero when any tap is intercepted. Both
are suitable as deploy gates.
